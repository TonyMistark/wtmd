# WYSIWYG 评估 — wtmd 要不要做所见即所得编辑

> **结论：不做完整 WYSIWYG。** 先把双视图做成「无损切换」（当前切换会丢位置，这才是大部分摩擦的来源），
> 需要时再加可选分栏；「轻量混合渲染」只在明确信号出现后，以最小切片（源码内联图片）重新评估。
>
> 评估基准：main `4cf5ec7`，189 项测试全绿。方法是读代码 + 跑现有用例，**未做用户访谈**——
> 所以第 5 节的触发信号里没有「用户说想要」这类无法证伪的依据。

## 1. 问题与边界

要回答的是：wtmd 要不要从「源码 / 预览双视图」跨到「编辑时即所见即所得」。

边界：

- 只讨论桌面端单文档编辑，不涉及移动端、协同编辑
- 只讨论「编辑体验」，不讨论导出与发布链路
- 不讨论富文本粘贴（Word → Markdown），那是另一个问题

## 2. 现状（代码事实）

| 能力 | 现状 | 位置 |
|---|---|---|
| 源码编辑 | `NSTextView`（TextKit 1）；高亮**就地改属性、绝不替换字符** | `EditorTextView.swift:406-413` |
| 专注模式 | layout manager 临时属性，不写 textStorage | `EditorTextView.swift:287` |
| 打字机模式 | 自绘 clip view 改写滚动夹取 | `EditorTextView.swift:372` |
| 预览 | `WKWebView`，块级增量替换，未变块 DOM 不动 | `PreviewView.swift:38-48`；`BlockDiff.swift`（52 行） |
| 模式切换 | `switch store.mode` **销毁并重建**视图 | `ContentView.swift:231-276` |
| 切换后的预览 | `makeNSView` → `reload()` → `loadHTMLString` | `PreviewView.swift:20-24, 112-125` |
| 图片 | 粘贴落盘 `assets/`，源码里插入 `![](assets/…png)` | `ImageAssets.swift:80-111`；`EditorTextView.swift:42` |
| 公式 | 源码是 `$…$`，预览由 KaTeX 渲染 | `HTMLRenderer.swift`（mathSpan）；`Theme.swift:430` |
| 表格 | 源码是 pipe 文本，预览是 GFM 表格 | `MarkdownParser.swift`（451 行） |
| 渲染管线 | 自研解析 + 渲染 + 统计，零第三方依赖 | `WTMarkdownKit` 共 1,100 行 |

两条从代码里读出来、和「要不要 WYSIWYG」直接相关的事实：

1. **⌘/ 切换会重建视图**：`ContentView` 用 `switch store.mode` 分别构造编辑器与预览，
   预览的 `makeNSView` 会 `reload()` 整页重新加载——**滚动位置回到文首**，编辑器侧的
   选区与光标也随视图重建而丢失。写作者感受到的「打断」，一大半来自这里。
2. **源码视图里看不到图片、公式、表格的真实形态**：它们都只是文本（`![](...)`、`$…$`、pipe 表格），
   这是「纯文本是唯一真相」的直接代价，不是疏漏。

## 3. WYSIWYG 到底补什么

把「想要 WYSIWYG」拆成四类诉求，逐条对照现状：

| 诉求 | 现状能否满足 | 缺口性质 |
|---|---|---|
| 想看到成文的样子 | 能，⌘/ 一次按键；预览主题即时生效 | 无 |
| 想知道「我编辑的位置」在成文里的位置 | 不能，切换后回到文首 | **位置丢失**，与渲染无关 |
| 想直接改表格、挪图片 | 不能，要改 pipe 文本 / 路径 | 结构化编辑，真正的 WYSIWYG 价值 |
| 想调公式 | 半能，改完等 250ms 防抖看预览 | 反馈延迟，但可接受 |

结论很清楚：**第 2 行是最大公约数，且它不需要 WYSIWYG 就能修**。第 3 行才是 WYSIWYG
不可替代的部分，但它只覆盖「表格 + 图片」两块——撑不起一次编辑器重写。

## 4. 三条技术路线

### A. WebView contenteditable（Typora 式）

把编辑器换成 `contenteditable` 的 HTML，输入的是 DOM，存盘前再序列化回 Markdown。

- **核心难点是反向序列化**：本项目解析器是单向的（Markdown → 块 → HTML，`MarkdownParser.swift` 451 行），
  没有 HTML → Markdown 的序列化器。要保证 round-trip 保真，至少得覆盖表格对齐、脚注定义与引用、
  `[TOC]` 占位、mermaid 围栏的 info string、数学定界符、代码围栏语言、链接 title……
- **失败模式不可接受**：序列化只要有一处不保真，用户保存后源文件就被**静默改坏**。
  对一个以「源文件是纯文本、可被任何工具读取」为契约的写作工具，这是最坏的失败形态。
- **现有不变式全部推翻**：`#wtmd-content` 顶层子节点数不变式、BlockDiff 增量、主题变量层、导出、
  统计、以及刚修完的 IME 路径（#45）都要在 WebView 里重做并重新验证。
- 粗略成本：15–25 人日，外加长期维护（WebKit 行为差异、输入法差异）。

### B. TextKit 2 自定义布局（原生路线）

保留 `NSTextView`，迁到 TextKit 2，为标题/列表/引用/表格/代码/图片/公式分别实现布局片段。

- 现有编辑器是 TextKit 1（`layoutManager.addTemporaryAttribute`，`EditorTextView.swift:287`），
  专注模式、打字机、高亮全部依赖 TextKit 1 的行为——迁移等于重写编辑器。
- 表格要自己做单元格布局、命中测试、光标移动；图片/公式要自绘并处理尺寸回填。
- 粗略成本：20+ 人日，且没有现成参考实现可抄。

### C. 轻量混合（源码仍是源码，局部「看起来像成文」）

不换文本模型，只在源码视图里给图片/公式加视觉呈现（Typora 的一个子集）。

- **不能往 textStorage 插 `NSTextAttachment`**：那会改变字符数与光标映射，直接破坏 IME（#45 刚修）、
  选区、增量渲染与导出。只能走临时属性 + 自定义绘制，风险集中在坐标系与命中测试。
- 公式内联需要离屏 KaTeX 快照 + 缓存 + 尺寸测量回填，异步链路长。
- 表格仍然无解（除非走到 A/B 的复杂度）。
- 粗略成本：5–8 人日，收益只覆盖图片与公式。

### 对比

| 路线 | 覆盖场景 | 保真风险 | 对现有不变式的冲击 | 粗略成本 |
|---|---|---|---|---|
| A. contenteditable | 全部 | **高**（可能静默改坏源文件） | 编辑器、增量、导出、IME 全重做 | 15–25 人日 |
| B. TextKit 2 | 全部 | 低 | 编辑器重写，预览链路不动 | 20+ 人日 |
| C. 轻量混合 | 图片、公式 | 无（文本模型不变） | 光标/选区/绘制，需严格回归 | 5–8 人日 |

## 5. 决策

**不做完整 WYSIWYG（A 与 B 都否）。** 三条理由，按权重排序：

1. **代价不对称**：WYSIWYG 的价值是「编辑更顺」，失败代价是「文档被改坏」。写作工具里后者一票否决。
2. **收益不覆盖成本**：真正只有 WYSIWYG 能解决的只剩表格与图片的结构化编辑；其余诉求
   （看成文、定位）用双视图 + 位置保持就能满足。
3. **预算**：15–25 人日约等于 v0.4 + v0.5 的全部余量，而它服务的是少数场景。

**改为先做两件低成本的事**（建议进 v0.5 的 P1，不在本版）：

1. **双视图无损切换**：记住预览的滚动锚点与编辑器的选区，切换回来原地继续。
   现状是视图重建 + 整页重载（`ContentView.swift:231-276`、`PreviewView.swift:112-125`），
   改动面小，收益直接命中第 3 节里最大的那一行。
2. **可选分栏**（源码 ｜ 预览）：直接复用 `PreviewView`，让「对照」不必来回切。需评估窄窗口下的排版。

**重新评估「轻量混合」的触发信号**（任一成立才启动，不预先排期）：

- 分栏上线后，仍有 ≥3 个独立 issue 指向「源码里看不到图片/公式/表格」
- 出现稳定的「导出 Word 后再排版」工作流（说明用户在别处补排版，等于用脚投票）
- 有可复现的竞品对比证据表明 WYSIWYG 是用户选择其他工具的主因（需要真实访谈，不接受猜测）

## 6. 如果启动：最小切片与验收

若触发信号成立，**第一步只做「源码内联图片」**，不碰表格与公式：

- 图片以自绘方式出现在 `![](...)` 所在行；文本模型零改动，关掉开关完全回到现状
- 光标不进入图片区域；点击图片等同于把光标放到该行
- 验收必须包含四条既有不变式的回归：IME（#45 的 7 项用例）、选区/光标映射、
  增量渲染（顶层块数不变）、导出 HTML
- 明确**不做**：表格内联、公式内联、隐藏语法符号（Typora 式）——那是完整 WYSIWYG 的第一步，
  不属于「轻量」
