# wtmd v0.4 规划 — 从一间书房，到一部书稿

> v0.3 让 wtmd 成为常驻的写作工位；v0.4 要让工位上写得出更厚的文档：`[TOC]` 给长文一副随写随更新的骨架，KaTeX 让学术表达在预览里所见即所得——而源文件里永远还是纯文本。

**状态**：规划中 ｜ 前置：v0.3.0 已发布（2026-10-17，详见 [V03_PLAN.md](V03_PLAN.md)）

## 版本主题

| 特性 | 哲学落点 |
|---|---|
| `[TOC]` 目录语法 | 结构浮现——长文的骨架自己长出来，作者只管往下写 |
| KaTeX 数学公式 | 纯文本本质——公式也是文本，渲染是视图、不是内容 |
| WYSIWYG 评估 | 写作即排版——先回答「边界在哪里」，再决定要不要跨过去 |

## P0 — 核心特性（本版本必做）

### 1. `[TOC]` 目录语法

**用户故事**：作为长文写作者，我希望在文中任意位置写一行 `[TOC]`，预览里自动长出可点击的目录，导出的 HTML 也带着它。

- 块级占位：独占一行的 `[TOC]` 渲染为目录（标题层级嵌套列表，点击锚点跳转）
- 解析器：块级阶段识别占位；渲染时用 AST 已有的标题信息注入大纲（**零额外解析**）
- 空标题文档渲染为空目录占位，不报错
- 导出 HTML 携带静态目录（离线可跳转）；打印/存 PDF 同样出目录
- **实现要点（本特性唯一的新难点）**：现有 `BlockDiff` 的隐含假设是「块间独立」——一个块的渲染结果只依赖自己的源码区间。TOC 块的内容来自**全文所有标题块**，改任何一处标题都得重渲染 TOC。方案方向：渲染层为 TOC 块记录「标题签名」（层级 + 文本的哈希），diff 阶段除自身源码变化外，标题签名变化也把 TOC 块列入重渲染清单。纯函数、可单测
- 侧栏大纲导航已存在（v0.1），`[TOC]` 面向**文中场景**（预览阅读 + 导出），两者不合并
- 工作量：S–M ｜ 测试：占位识别、标题增/删/改后 TOC 同步、空标题文档、增量 diff 正确性（TOC 不重复渲染、不漏渲染）

### 2. 数学公式（KaTeX）

**用户故事**：作为写讲义/论文的人，我希望 `$E=mc^2$` 在预览里直接是公式，而源文件里仍是一行纯文本。

- 行内 `$...$`、块级 `$$...$$`；`\$` 转义不触发；行内代码里的 `$` 不触发
- katex.min.js + 字体**本地内嵌**（SPM 资源），**按需注入**——仅文档含公式时才注入，复用 mermaid 模式
- 渲染失败降级为原文本并提示错误（同 mermaid 的降级路径）
- **前置验证（开工第一件事，通过才继续）**：KaTeX 与增量渲染不变式的兼容性——渲染不得增删 `#wtmd-content` 顶层子节点；失败节点要清理（mermaid 往 body 泄漏脏块的教训直接平移）；离屏 WKWebView 端到端用例 + 反向验证
- 打印 / 导出 HTML 同样出公式
- 工作量：M ｜ 风险：资源体积（JS + 字体约 1MB 级，按需注入缓解；app 与 DMG 体积增长可接受）、增量渲染适配

## P1 — 评估与候选

### 3. WYSIWYG 评估（只评估，不实现）

- 目标：回答「wtmd 要不要做所见即所得编辑」——现有双视图（`⌘/`）已覆盖多少 WYSIWYG 诉求？源码内联渲染（图片/公式直接在源码视图显示）的成本与风险？TextKit 与 WebView 混合的复杂度？
